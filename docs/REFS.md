# 引用完整性：`abook refs`

记录之间靠身份（身份 = 文件名干或 `ID` 字段）互相指向：`PROMOTED_FROM` 指来源候选、
`RELATED_IDS` 指相关条目、`SUPERSEDES` 指被取代的旧条目。这些字段写的是**另一条记录的身份**，
所以它们坏掉的方式很特殊：

**字段本身永远是合法的非空字符串。** 逐条校验看不出任何问题——只有把全库身份集建起来
对一遍，才知道它指得着指不着。

## 为什么必须由工具做

这件事模型手工做不可靠，原因有三个：

1. **旧库有多种身份形态。** 新库用 `<N|C>-<时间戳>-<哈希>`，旧库用 `AB2-C-001` 顺序号，
   还有 `N-20260930T160500-quotepair` 这种带语义尾巴的。少认一种就误报一大片。
2. **旧库字段会打包成一行。** `ID=N-xxx;PROJECT=y;TASK=z` 里，只有第一段是身份。
   按行取值的脚本会把后两段也当身份，于是"解析不到"。
3. **不是所有非空值都是身份。** 旧库的 `PROMOTED_FROM` 存来源文档路径
   （`References/core/x.md#某节`），`SUPERSEDES` 存自然语言描述
   （`旧按 Agent 与复杂度默认激活的行为`）。拿它们去查记录必然查不到，那是分类错误。

## 三种判定

```
abook refs                       只报告
abook refs --fix --dry-run       预演能修哪些
abook refs --fix --approve       执行（正式库需批准确认）
abook refs --json                机器可读
```

输出分三类：

- **可解析** —— 值在身份集里，正常。
- **真悬空** —— 值长得像身份，但库里没有。这才是问题。
- **非身份** —— 文档路径或描述文本，本来就不该查，不计入。

## 自动修复的边界

`--fix` 只修**能唯一推导**的，判据是时间戳：

改名而不改引用是悬空的主因——旧身份带语义尾巴 `N-20260930T160500-quotepair`，
改名后变成内容哈希 `N-20260930T160500-3a969b6d`。两者的时间戳部分完全相同，
因为时间戳是建档那一刻。

于是映射可以推出来，**但只在唯一时才算数**：

| 情况 | 处置 |
|---|---|
| 同前缀同时间戳恰好一条 | 改写为该条 |
| 同时间戳有多条 | 不动，报"无法判定" |
| 一条都没有 | 不动，报"目标记录不存在" |
| 形态本身解析不了 | 不动，报"形态无法解析" |

**能推的不问，推不出的不猜。** 猜错一个引用比留着悬空更坏：悬空是可见的，
错指是隐形的，后者会让"这条记录的来源"永久失真。

## 已知处置结果（本库实跑）

| 阶段 | 悬空数 |
|---|---|
| 初版（分类错误，把文档路径算进去） | 133 |
| 修正分类后 | 31 |
| `--fix` 之后 | 15 |

残余 15 处全部属于"记录确实被删"或"同时间戳多条"，工具如实报告、未擅改。

## 顺带抓到的三个 bug

这一轮做 `refs` 时暴露出三个与它无关、但更危险的问题：

1. **`--dry-run` 从未被读取。** `dry_run()` 只判断"有没有 apply/write/yes"，
   压根没看 `--dry-run` 这个参数。于是 `repair --apply --dry-run`（"先预演看看"的
   自然写法）会**真的写入**。一次本该只读的核对把库改了。
2. **`refs --fix --approve` 被自己的预演分支拦掉。** `dry_run()` 不认 `--fix`，
   参数齐全却什么都不做，还打印 `[dry-run]`。
3. **路径拼了两次 `records`。** `Lib::dir()` 返回的就是 `canonical/records`，
   再 `.join("records")` 变成 `canonical/records/records/`，于是"已修 0 条"。

三者共同点：**开关函数的判断范围与实际参数集不一致**。写入安全侧（`--dry-run`）
必须在最前面短路，不能与写入开关并列判断。
