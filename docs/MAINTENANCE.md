# 维护者须知

面向要改这个工具的人。用户手册见 `README.md`。

## 一、这个工具的本质危险

abook 修的是机械错误，而它的机械错误直接表现为**记忆丢失**。更麻烦的是，
它出错时往往仍然报成功：

| 曾经发生的事 | 症状 |
|---|---|
| `reconcile` 重写地图 | 522 条记录的分支名变成 `unclassified`，记录数报成 1 |
| `promote` 改地图 | 同上，且是在一次正常的晋升里发生的 |
| `repair --only id --apply` | 523 条逻辑 ID 全换成文件名，引用全断 |
| `split` 报 `INTEGRITY` | 报失败，但盘上数据已经被切开了 |
| 两个进程同时写 | 两个都 `rc=0`，地图和计数只记了其中一个 |
| 写入时无版本意识 | AI 读完之后别人改了，AI 的写入把对方改动静默覆盖 |

这些事的共同点：**操作者以为成功了**。所以改这个代码库时，判断标准不是
"命令返回 0"，而是"盘上的数据对不对"。每条写路径都要问：

1. 写之前，磁盘上的真实状态是什么？
2. 写之后，怎么证明内容符合预期？
3. 失败时，已经写下去的部分回滚了吗？如果没有，用户怎么知道数据已经变了？

第三点最容易被忽略。`split` 曾经在写盘成功之后返回失败——用户以为没生效，
于是重试（第二次报"分隔文本未找到"，因为已经被消费掉了），或者放弃，而数据
已经是半拆状态。失败可以，但**失败时不能让用户误判数据状态**。

## 二、数据格式的坑

### FILES 与 PATH 是两种布局，必须同时支持

地图里一张卡片有两种写法：

```
BRANCH=xxx
FILES=
  - ID-1|KIND|MATURITY|records/ID-1.md|标题
  - ID-2|KIND|MATURITY|records/ID-2.md|标题
```

或

```
BRANCH=xxx
PATH=candidate/records/a.md,candidate/records/b.md
```

真实库 960 条记录全用 `FILES`（canonical 522 条，candidate 436 条），而
`PATH=` 只有 4 行——且那 4 行描述的是一个目录，不是记录列表。

初版只读 `PATH`，于是工具认为每张卡都是空的。它接下来的行为完全符合逻辑：
"这张卡没记录，我把它改名成 unclassified 并重算记录数"——于是 522 条记录
在工具眼里消失了，文件还在。

`paths()`、`raw_paths()`、`set_paths*` 三个入口都要认 `FILES`，缺一个就会
出现"读得到但写不回去"或者"写回去变成另一种布局"。

### FILES 条目行的三个陷阱

**陷阱一：字段里可以有竖线。** 分隔是 `|`，但标题本身可能含 `|`。有两条例
外记录是 7 个字段而不是 5 个。所以解析要 `splitn(5, '|')`，不是 `split('|')`。

**陷阱二：标题里可以有等号。** `- ID|||path|根因=xxx` 这样的行，如果先按
`=` 切分，就会落进"不是合法 KEY=VALUE"的分支，被当成上一行的续行，追加到
上一个字段上。而卡片开头时"上一个字段"正是 `BRANCH`——分支名就变成了带换行
的记录正文。`FilesEntry::parse` 的判定必须在 `split_once('=')` **之前**。

**陷阱三：空的 `FILES=` 会吃掉上面的条目。** 一张卡里如果先有若干条目行、
再出现一个空的 `FILES=` 标记，把空值赋给 `FILES` 会清掉已收集的内容。真实库
有一张卡因此从 59 条掉到 44 条。空标记遇到已有条目必须跳过。

### 四处计数

记录数在四个地方各写了一遍：`Global.md` 头部、`Global.md` 正文、
`Index.md` 头部、`Atlas.md` 的 `RECORD_COUNT`。只同步一处就会分叉。

还有一个坑：真实文件用的是 `[MEMORY_FILE_CONTENTS]` 标签，而 `BookFile::load`
只认 `[MEMORY_BOOK_V2]`。用错识别方式会把计数写进正文区而不是头部——文件里
看着有两个计数，改的是错的那个。

### 旧式打包行

早期记录把多个字段写在一行里：

```
ID=AB2-OC-045;PROJECT=dsh-node-service-guardian;TASK=skill-hardening;SEQUENCE=045
```

解析器会把 `;` 后能解析成 `KEY=` 的部分切开，所以这些字段其实读得到。但
`grep '^RELATED_IDS='` 之类的行首匹配抓不到它们，排障时容易误判"这个字段不存在"。

`repair --only sep` 会把它们拆成独立行。这条路径实测 960 条记录、字段值零丢失，
但它一次会改 376 个文件——在真实库上跑之前先 `--dry-run` 看清楚。

### `;` 分隔的门控

旧式打包行的切分条件是"`;` 后面能解析成合法键"。这在遇到 URL 时失效：

```
SUMMARY=…/gitweb?p=5G/T830/mt6990.git;a=shortlog;h=refs/heads/xxx）…
```

`a=shortlog` 和 `h=refs/...` 都被当成新字段，`SUMMARY` 被截断成 44 个字符，
剩下半句跑进伪造的 `H` 字段。修法是只让**已知键**触发切分——补完 `KNOWN_KEYS`
之后实测 6371 处 `;` 分隔里只有这 4 处不再切分，精确命中损伤，不动其它记录。

顺序很重要：先补名字表，再收紧门控。反过来会让 `;RELATED_CANDIDATES=` 这类
真字段被并进上一个值，制造新的损伤。

## 三、并发

### 库级锁

所有写命令在 `main` 分发处统一加锁，冲突时**排队等待**而不是失败。这点是刻
意的：失败会让等待的 AI 重发整条命令，而它那次的读是在旧版本上做的，重发只会
放大问题。

锁用 `flock`。曾经因为 `std::process::exit()` 跳过析构函数导致锁文件永不释放
——所有后续命令都会卡住。现在显式释放，`Drop` 里兜底。

### 读-改-写竞态（最隐蔽的一类）

锁只解决 abook 与 abook 之间的问题。真正的危险窗口是：

```
AI 读记录  →  AI 思考几分钟  →  AI 发出写入命令
                  ↑
            别的会话/进程/编辑器在这里改过它
```

任何"在命令开始时重新读文件"的校验都会通过，因为命令启动时磁盘已经是最新
的了——分叉发生在命令开始之前。

唯一有效的办法是让版本号跨越这个窗口：

- 读取时（`show`/`cat`）打印 `[version xxxxxxxx]`，并在 `--json` 里给 `version` 字段
- 写入时收 `--if-version`，与磁盘不符即拒绝，说明"你读到 X，现在是 Y"
- 也可以用三方合并：`merge.rs` 做行级 diff，两侧改动落在不相交区间时自动合并，
  重叠才拒绝，拒绝时保留双方内容

`--if-version` 缺省不校验（保持既有脚本兼容）。这是有意的取舍：强制会让所有
现存调用失败，而它们本来也没有版本意识。

## 四、自检

```sh
abook selftest
```

当前 139 通过 / 0 失败 / 3 跳过。

自检本身也出过三次错，都值得记住教训：

1. **硬编码版本号。** 断言里写 `"abook 1.0.0"`，而 `Cargo.toml` 的版本长期没
   更新，二进制一直自称 1.0.0。修好版本号之后自检反而失败了。
2. **收集器比解析器宽松。** 字段名检查用 `line.split(';')` 加 `trim()`，把正文
   里的 `TOKEN = re.compile(...)` 认成字段 `TOKEN`，报了 12 个不存在的"未知字
   段"。改成直接调用 `Record::parse_str`，检查口径与被检查对象一致。
3. **分页断言依赖真实数据。** 断言要求第 1 页和第 2 页内容不同，但真实库
   `review/` 只有 1 个文件，越界页被夹回第 1 页。改成用临时 root 造 3 条夹具。

共同教训：**自检不能依赖被测库的当前形态**，也不能自己实现一套与被测代码
不同的判断逻辑。否则它报的 FAIL 会把人引向不存在的问题——我就是这样被误导了
两轮。

## 五、性能

要求是"所有操作都保持行业内领先的效率和功耗开销"。当前的现实约束：

- 库规模约 960 条记录，`Global.md` 与 `Index.md` 各几十 KB，两个 `Atlas.md`
  各几百 KB
- 实测：`show` 单次约 14 ms，`state` 约 97 ms，全库 `search` 约 83 ms
- 二进制静态链接，启动到第一行输出有几毫秒量级的固定开销

已经做过的优化：`digest_prefix` 原先算完 64 字符再截 8 位，现在只哈希需要的
字节数。它在 `show`/`cat`/`get` 和记录 ID 派生里都在热路径上。

改代码时的自检线：**任何命令都不应该为了回答一个问题而解析整个库**。如果确实
需要全库信息（`state`、`audit`、`selftest` 需要），那可以接受；但 `show` 一条
记录不该读 960 个文件。

## 六、发版

### 版本号跟随 git tag

二进制自报的版本来自编译期常量，而这个常量曾经写死在 `Cargo.toml` 里且从未跟
随标签更新——标签发到 `v1.6.1`，二进制仍然自称 `1.0.0`。现在 `build.rs` 从
`git describe --tags` 取，CI 里有一道校验防止再脱节。

发版步骤：

```sh
git tag v1.6.2
git push origin v1.6.2
```

CI 会构建全部目标架构并把产物推到 `downloads` 分支（单孤儿提交 force push，
不做增量，仓库不会随发版长胖）。少于 15 个二进制时该作业直接失败、不覆盖分支
——宁可这次不更新，也不让固定地址出现残缺。

### 本地与远程的关系

方向是**远程 → 本地**。发版流程一次构建 15 个架构，本机架构只是其中之一，
其余 14 个只存在于远程。所以远程那份才是权威构建，本机编完要用
`sync-from-remote.sh` 核对并以远程为准替换本地安装。

不要反过来让远程对齐本地——本机只能编一个架构，做不到。也不要因为源码指纹
相同就假定字节相同：同源不等于同字节。

## 七、改动这个代码库时

1. 所有实验在副本上做。`ABOOK_ROOT=<路径>` 指定库根，**只 `cd` 不隔离**——
   这是真实库被自伤两次的直接原因。
2. 真实库是 `/root/AgentsBook`。改完代码先在那里跑一次 `state` 看一致性。
3. 涉及地图或计数的写路径，必须验证四处计数一致。
4. 涉及写入的命令，必须验证失败时数据状态可判定。
5. 提交前跑 `abook selftest`，并确认它没有因为你的改动而降低判定标准。

## 八、缺陷史

按出现顺序，都是真实发生过的：

| 缺陷 | 根因 | 修法 |
|---|---|---|
| 地图计数归零、分支并入 unclassified | `paths()` 不读 `FILES` | 三个入口统一识别两种布局 |
| 分支名带换行、move 建重复卡 | 条目行先被 `=` 切分 | 判定提到 split 之前 |
| 卡片条目从 59 掉到 44 | 空 `FILES=` 清掉已有列表 | 空标记遇到已有条目跳过 |
| 新增条目 `id\|\|\|path\|` | 只设了 id 和 path | 带上真实 kind/maturity/title |
| 同一条记录出现在两个分支 | 只查目标分支 | 全库查重，一条记录一个分支 |
| 四处计数分叉 | 只同步一处，且认错头部标签 | 一个函数改两文件两位置 |
| 并发写丢计数 | 无锁 | 库级锁，排队不失败 |
| 锁永不释放 | `process::exit` 跳过 `Drop` | 显式释放 + `Drop` 兜底 |
| 523 条逻辑 ID 被换成文件名 | `is_scheme_name` 只认时间戳形态 | ID 只在为空时补 |
| `split` 报失败但已写盘 | 复读比较未忽略尾部换行 | 忽略尾部空白，报错写明已改 |
| `SUMMARY` 被截断成 44 字符 | `;a=shortlog` 被当成新字段 | 只让已知键触发 `;` 切分 |
| 静默覆盖他人改动 | 校验在命令内重读文件 | 版本号跨命令传递 + 三方合并 |
| 二进制自称 1.0.0 | `Cargo.toml` 从不更新 | 跟随 git tag + CI 校验 |
| 自检三个 FAIL 来自它自己 | 硬编码、判定宽松、依赖真实数据 | 逐一改成不依赖真实数据 |
| 任意文件可被改写 | `skill decide` 的候选名直接拼进路径 | 拒绝含路径的文件名 |
| `attach add --dry-run` 照样写盘 | add/commit 没有 dry-run 分支，且 main 见 dry-run 跳过锁 | 两处都补真 dry-run |
| 5MB 附件改中间字节报"内容没变" | 指纹只读头尾；改成 16 块抽样仍有空隙 | 不再抽样，全量哈希 |
| `update` 与其它命令四处分叉 | 唯一手写自己那套写盘流程 | 改走 `save()` |
| `set` 能写入身份字段 | 通用后门没有护栏 | ID/STATUS/FORMAT 三类拒绝并指路 |
| `move` 拼错分支会新建分支 | 创建分支是副作用 | 只由 `branch add` 做 |
| `branch`/`doctor`/`refs` 不加锁 | 漏在写命令列表外 | 补入 |

## 九、一条反复出错的推理

大文件指纹改了三版，每版都比上一版更像回事，但都错在同一个地方：

1. 头 64KB + 尾 64KB —— 改中间就漏
2. 16 块均匀抽样 —— 块间有空隙，落在空隙里照样漏（实测第 2500000 字节）
3. 全量哈希 —— 对

前两版的推理都是"没人会那样改"，而这条链路的失败形态是**证据已被改，工具
回答没变**。附件是记录携带的原始证据，证据坏了却报完好，比误报更坏，因为它
让人停止怀疑。空隙是数学上不可避免的：要么覆盖全部，要么留缝。

成本实测划得来：逐字节 FNV-1a 约 500MB/s，5MB 约 10ms，50MB 约 100ms。

## 十、另一种假动作

`attach add --dry-run` 曾经真的复制文件、回写清单、刷新 UPDATED、写 commit，
而且因为 `main` 见 `--dry-run` 就跳过库锁，它还是在**无锁**状态下改库。

比没有这个开关更坏：一个叫"只看看会发生什么"的开关做了真事，用的人从此不会
再相信 dry-run。凡是有 `--dry-run` 的命令，其分支必须在任何写盘之前返回，这
一条应该由自检覆盖而不是靠自觉。
