# 维护者须知

面向要改这个工具的人。用户手册见 `README.md`。

## 一、这个工具的本质危险

abook 修的是机械错误，而它的机械错误直接表现为**记忆丢失**。更麻烦的是，
它出错时往往仍然报成功：

| 曾经发生的事 | 症状 |
|---|---|
| `reconcile` 重写地图 | 522 条记录的分支名变成 `unclassified`，记录数报成 1 |
| `promote` 改地图 | 同上，且是在一次正常的晋升里发生的 |
| `repair --only id --apply` | 523 条逻辑 ID 全换成文件名，引用全断 |
| `split` 报 `INTEGRITY` | 报失败，但盘上数据已经被切开了 |
| 两个进程同时写 | 两个都 `rc=0`，地图和计数只记了其中一个 |
| 写入时无版本意识 | AI 读完之后别人改了，AI 的写入把对方改动静默覆盖 |

这些事的共同点：**操作者以为成功了**。所以改这个代码库时，判断标准不是
"命令返回 0"，而是"盘上的数据对不对"。每条写路径都要问：

1. 写之前，磁盘上的真实状态是什么？
2. 写之后，怎么证明内容符合预期？
3. 失败时，已经写下去的部分回滚了吗？如果没有，用户怎么知道数据已经变了？

第三点最容易被忽略。`split` 曾经在写盘成功之后返回失败——用户以为没生效，
于是重试（第二次报"分隔文本未找到"，因为已经被消费掉了），或者放弃，而数据
已经是半拆状态。失败可以，但**失败时不能让用户误判数据状态**。

## 二、数据格式的坑

### FILES 与 PATH 是两种布局，必须同时支持

地图里一张卡片有两种写法：

```
BRANCH=xxx
FILES=
  - ID-1|KIND|MATURITY|records/ID-1.md|标题
  - ID-2|KIND|MATURITY|records/ID-2.md|标题
```

或

```
BRANCH=xxx
PATH=candidate/records/a.md,candidate/records/b.md
```

真实库 960 条记录全用 `FILES`（canonical 522 条，candidate 436 条），而
`PATH=` 只有 4 行——且那 4 行描述的是一个目录，不是记录列表。

初版只读 `PATH`，于是工具认为每张卡都是空的。它接下来的行为完全符合逻辑：
"这张卡没记录，我把它改名成 unclassified 并重算记录数"——于是 522 条记录
在工具眼里消失了，文件还在。

`paths()`、`raw_paths()`、`set_paths*` 三个入口都要认 `FILES`，缺一个就会
出现"读得到但写不回去"或者"写回去变成另一种布局"。

### FILES 条目行的三个陷阱

**陷阱一：字段里可以有竖线。** 分隔是 `|`，但标题本身可能含 `|`。有两条例
外记录是 7 个字段而不是 5 个。所以解析要 `splitn(5, '|')`，不是 `split('|')`。

**陷阱二：标题里可以有等号。** `- ID|||path|根因=xxx` 这样的行，如果先按
`=` 切分，就会落进"不是合法 KEY=VALUE"的分支，被当成上一行的续行，追加到
上一个字段上。而卡片开头时"上一个字段"正是 `BRANCH`——分支名就变成了带换行
的记录正文。`FilesEntry::parse` 的判定必须在 `split_once('=')` **之前**。

**陷阱三：空的 `FILES=` 会吃掉上面的条目。** 一张卡里如果先有若干条目行、
再出现一个空的 `FILES=` 标记，把空值赋给 `FILES` 会清掉已收集的内容。真实库
有一张卡因此从 59 条掉到 44 条。空标记遇到已有条目必须跳过。

### 四处计数

记录数在四个地方各写了一遍：`Global.md` 头部、`Global.md` 正文、
`Index.md` 头部、`Atlas.md` 的 `RECORD_COUNT`。只同步一处就会分叉。

还有一个坑：真实文件用的是 `[MEMORY_FILE_CONTENTS]` 标签，而 `BookFile::load`
只认 `[MEMORY_BOOK_V2]`。用错识别方式会把计数写进正文区而不是头部——文件里
看着有两个计数，改的是错的那个。

### 旧式打包行

早期记录把多个字段写在一行里：

```
ID=AB2-OC-045;PROJECT=dsh-node-service-guardian;TASK=skill-hardening;SEQUENCE=045
```

解析器会把 `;` 后能解析成 `KEY=` 的部分切开，所以这些字段其实读得到。但
`grep '^RELATED_IDS='` 之类的行首匹配抓不到它们，排障时容易误判"这个字段不存在"。

`repair --only sep` 会把它们拆成独立行。这条路径实测 960 条记录、字段值零丢失，
但它一次会改 376 个文件——在真实库上跑之前先 `--dry-run` 看清楚。

### `;` 分隔的门控

旧式打包行的切分条件是"`;` 后面能解析成合法键"。这在遇到 URL 时失效：

```
SUMMARY=…/gitweb?p=5G/T830/mt6990.git;a=shortlog;h=refs/heads/xxx）…
```

`a=shortlog` 和 `h=refs/...` 都被当成新字段，`SUMMARY` 被截断成 44 个字符，
剩下半句跑进伪造的 `H` 字段。修法是只让**已知键**触发切分——补完 `KNOWN_KEYS`
之后实测 6371 处 `;` 分隔里只有这 4 处不再切分，精确命中损伤，不动其它记录。

顺序很重要：先补名字表，再收紧门控。反过来会让 `;RELATED_CANDIDATES=` 这类
真字段被并进上一个值，制造新的损伤。

## 三、并发

### 库级锁

所有写命令在 `main` 分发处统一加锁，冲突时**排队等待**而不是失败。这点是刻
意的：失败会让等待的 AI 重发整条命令，而它那次的读是在旧版本上做的，重发只会
放大问题。

**实现不是 `flock`，是 `O_EXCL` 独占创建。**（本节早前写成 `flock`，与代码不符，
已按 `util.rs` 的 `LibLock::acquire` 更正。）锁文件是库根的 `.abook.lock`，
用 `OpenOptions::create_new(true)` 创建——内核保证同名创建只有一个能成功，
不需要额外依赖。选它而不是 `flock` 的理由：跨平台、无外部 crate，且崩溃时
内核会关掉句柄，不会留下永远打不开的锁。

**失效锁判定（两档，不是单纯看年龄）**：

| 情况 | 判据 | 处置 |
|---|---|---|
| 锁里 pid 可读，且进程已死 | `pid > 0 && !pid_alive(pid)` | 立即打破，不必等满 600 秒 |
| 锁里读不到 pid | 年龄 > `STALE_LOCK_SECS`（600 秒） | 打破 |
| pid 可读但进程还活着 | — | **绝不打破**，继续等 |

第三行是关键：曾经的条件是 `aged && dead`，等于「已经死了也得等十分钟」，下次
写库的人被白白挡十次 30 秒。而年龄只在**判断不了是否存活**时才有意义——宁可
多等，也不能抢走一个正在跑长任务的活锁。

**实测并发上限**（2026-10-28，aarch64 真机）：

```
8  进程同时 write  → 8/8 成功，候选 8 条，state 报 8
20 进程同时 write  → 20/20 成功，候选 20 条，state 报 20
```

写入条数、磁盘文件数、`Index.md` 路由数三者一致——说明锁确实串行化了
「读 Atlas → 改 → 写回 → 改 Index → 改 Global」这套跨文件读改写，没有丢更新。
写完后 `.abook.lock` 自动消失，无需人工清理。

### 加索引时不能破坏并发

`.index/` 落盘索引（见第 05 节方案）挂在写命令上增量维护，因此它***必须***在
库级锁内完成，和 Atlas/Index/Global 的更新是同一个临界区。理由：

- 索引和记录文件是两个需要保持一致的东西。如果索引更新在锁外做，A 进程写完
  记录、还没写索引时，B 进程可能已经按旧索引召回，读到的是「记录存在但索引
  里没有」的中间态。
- 反过来也一样：索引先于记录落盘，会指向一个还不存在的记录。

所以规则是：**记录与索引要么一起成功，要么一起回滚**，且都在同一把锁下。
若索引更新失败，正确做法是标记索引失效（`meta.json` 里写 `dirty: true`）并在
下次写入时全量重建，而不是让写整体失败——记录是资产，索引是派生物，不能因为
派生物坏了就拒绝记账。

### 并发下的索引重建

两个进程同时发现索引失效会都想重建。重建结果是幂等的，但会互相覆盖写。
用同一个 `.abook.lock` 串行化即可；重建耗时实测 121ms（851 条 / 4.28 MB），
在锁内做完全可接受。不要为重建单独设计一套锁——多一把锁就多一种死锁可能。

### 落盘索引 `.index/` 与并发

索引挂在 `main` 的写命令出口统一维护，**仍在库级锁内**。三条规则：

1. **更新在锁内。** 索引与记录是两份需要一致的东西，锁外更新会出现
   「记录已写、索引未写」的中间态，别的进程按旧索引召回就读到不一致。
2. **失败不阻断写入。** 索引写失败只标 `dirty`，下次重建。记录是资产、
   索引是派生物，不能因为派生物坏了就拒绝记账。
3. **重建不另起锁。** 复用同一把 `.abook.lock`。重建是 O(n)，2 万条约 2 秒，
   在锁内可接受；多一把锁就多一种死锁可能。

### 对账判据：为什么是文件名指纹

`Index::load` 要判断"索引还属不属于当前这个库"。三种判据都试过：

| 判据 | 问题 |
|---|---|
| 逐文件 `metadata()` | 2 万条要 3.5 秒。守卫比被守的东西贵。 |
| 目录 mtime | 复制/解压/git checkout/rsync 都会改它 → **迁移一次索引就失效** |
| 只数条数 | 同数量改名或替换发现不了 |

现在用「条数 + 文件名 FNV 哈希」。它同时满足三条：复制不改名所以稳定、
只 readdir 不 stat 所以便宜、对增删改名敏感。abook 的记录名是
「时间戳-内容哈希」，所以文件名本身带内容指纹——不改名就不会改内容。

> 这条踩过真坑：一度用目录 mtime，迁移后查询从 48ms 退到 262ms（走回退重建），
> 而"整目录换机器还能用"是明确要求。

### 索引的边界

**只索引记忆条目，不索引附件。** `<stem>-refs/`、`-assets/` 等目录不进索引：
条目正文已记录它们带了什么，再索引一遍是重复记账；且附件类型异构（二进制、
压缩包、视频），做分词要么无意义要么读不了。

注意这条理由**不是性能**。实测 2000 条全带附件只比无附件多 15ms，因为
`attach::scan` 只对命中的记录执行。两件事要分开记，否则以后有人会拿
"附件扫描很快"去论证"索引没必要"——那是两个命题。

### 判断"要不要维护索引"的坑

写命令跑完后是否维护索引，判据踩过两个坑，都由 `selftest` 抓出：

- 只用 `dry_run()` → 它把"没有 `--apply`"当预演，而 `write` 本来就不要
  `--apply`（写一条记录是本职）。结果索引永远不生成。
- 只看 `--dry-run` → `refresh`/`recount`/`normalize`/`repair` 默认预演、
  要 `--apply` 才写，漏判会在预演时生成索引，破坏"预演不碰磁盘"。

现在的判据：显式 `--dry-run` 一律不算写；其余按命令性质分——"修复/重算"类
（`refresh`/`recount`/`normalize`/`repair`/`refs`/`doctor`/`branch`/`leftover`）
看 `--apply`，其余写命令按本职算写。

### 读-改-写竞态（最隐蔽的一类）

锁只解决 abook 与 abook 之间的问题。真正的危险窗口是：

```
AI 读记录  →  AI 思考几分钟  →  AI 发出写入命令
                  ↑
            别的会话/进程/编辑器在这里改过它
```

任何"在命令开始时重新读文件"的校验都会通过，因为命令启动时磁盘已经是最新
的了——分叉发生在命令开始之前。

唯一有效的办法是让版本号跨越这个窗口：

- 读取时（`show`/`cat`）打印 `[version xxxxxxxx]`，并在 `--json` 里给 `version` 字段
- 写入时收 `--if-version`，与磁盘不符即拒绝，说明"你读到 X，现在是 Y"
- 也可以用三方合并：`merge.rs` 做行级 diff，两侧改动落在不相交区间时自动合并，
  重叠才拒绝，拒绝时保留双方内容

`--if-version` 缺省不校验（保持既有脚本兼容）。这是有意的取舍：强制会让所有
现存调用失败，而它们本来也没有版本意识。

## 四、自检

```sh
abook selftest
```

当前 143 通过 / 0 失败 / 3 跳过（仓库内的二进制会多跑 3 项）。

自检本身也出过三次错，都值得记住教训：

1. **硬编码版本号。** 断言里写 `"abook 1.0.0"`，而 `Cargo.toml` 的版本长期没
   更新，二进制一直自称 1.0.0。修好版本号之后自检反而失败了。
2. **收集器比解析器宽松。** 字段名检查用 `line.split(';')` 加 `trim()`，把正文
   里的 `TOKEN = re.compile(...)` 认成字段 `TOKEN`，报了 12 个不存在的"未知字
   段"。改成直接调用 `Record::parse_str`，检查口径与被检查对象一致。
3. **分页断言依赖真实数据。** 断言要求第 1 页和第 2 页内容不同，但真实库
   `review/` 只有 1 个文件，越界页被夹回第 1 页。改成用临时 root 造 3 条夹具。

共同教训：**自检不能依赖被测库的当前形态**，也不能自己实现一套与被测代码
不同的判断逻辑。否则它报的 FAIL 会把人引向不存在的问题——我就是这样被误导了
两轮。

## 五、性能

要求是"所有操作都保持行业内领先的效率和功耗开销"。当前的现实约束：

- 库规模约 960 条记录，`Global.md` 与 `Index.md` 各几十 KB，两个 `Atlas.md`
  各几百 KB
- 实测：`show` 单次约 14 ms，`state` 约 97 ms，全库 `search` 约 83 ms
- 二进制静态链接，启动到第一行输出有几毫秒量级的固定开销

已经做过的优化：`digest_prefix` 原先算完 64 字符再截 8 位，现在只哈希需要的
字节数。它在 `show`/`cat`/`get` 和记录 ID 派生里都在热路径上。

改代码时的自检线：**任何命令都不应该为了回答一个问题而解析整个库**。如果确实
需要全库信息（`state`、`audit`、`selftest` 需要），那可以接受；但 `show` 一条
记录不该读 960 个文件。

## 六、发版

### 版本号跟随 git tag

二进制自报的版本来自编译期常量，而这个常量曾经写死在 `Cargo.toml` 里且从未跟
随标签更新——标签发到 `v1.6.1`，二进制仍然自称 `1.0.0`。现在 `build.rs` 从
`git describe --tags` 取，CI 里有一道校验防止再脱节。

发版步骤：

```sh
git tag v1.6.2
git push origin v1.6.2
```

CI 会构建全部目标架构并把产物推到 `downloads` 分支（单孤儿提交 force push，
不做增量，仓库不会随发版长胖）。少于 15 个二进制时该作业直接失败、不覆盖分支
——宁可这次不更新，也不让固定地址出现残缺。

### 本地与远程的关系

方向是**远程 → 本地**。发版流程一次构建 15 个架构，本机架构只是其中之一，
其余 14 个只存在于远程。所以远程那份才是权威构建，本机编完要用
`sync-from-remote.sh` 核对并以远程为准替换本地安装。

不要反过来让远程对齐本地——本机只能编一个架构，做不到。也不要因为源码指纹
相同就假定字节相同：同源不等于同字节。

## 七、改动这个代码库时

1. 所有实验在副本上做。`ABOOK_ROOT=<路径>` 指定库根，**只 `cd` 不隔离**——
   这是真实库被自伤两次的直接原因。
2. 真实库是 `/root/AgentsBook`。改完代码先在那里跑一次 `state` 看一致性。
3. 涉及地图或计数的写路径，必须验证四处计数一致。
4. 涉及写入的命令，必须验证失败时数据状态可判定。
5. 提交前跑 `abook selftest`，并确认它没有因为你的改动而降低判定标准。

## 八、缺陷史

按出现顺序，都是真实发生过的：

| 缺陷 | 根因 | 修法 |
|---|---|---|
| 地图计数归零、分支并入 unclassified | `paths()` 不读 `FILES` | 三个入口统一识别两种布局 |
| 分支名带换行、move 建重复卡 | 条目行先被 `=` 切分 | 判定提到 split 之前 |
| 卡片条目从 59 掉到 44 | 空 `FILES=` 清掉已有列表 | 空标记遇到已有条目跳过 |
| 新增条目 `id\|\|\|path\|` | 只设了 id 和 path | 带上真实 kind/maturity/title |
| 同一条记录出现在两个分支 | 只查目标分支 | 全库查重，一条记录一个分支 |
| 四处计数分叉 | 只同步一处，且认错头部标签 | 一个函数改两文件两位置 |
| 并发写丢计数 | 无锁 | 库级锁，排队不失败 |
| 锁永不释放 | `process::exit` 跳过 `Drop` | 显式释放 + `Drop` 兜底 |
| 523 条逻辑 ID 被换成文件名 | `is_scheme_name` 只认时间戳形态 | ID 只在为空时补 |
| `split` 报失败但已写盘 | 复读比较未忽略尾部换行 | 忽略尾部空白，报错写明已改 |
| `SUMMARY` 被截断成 44 字符 | `;a=shortlog` 被当成新字段 | 只让已知键触发 `;` 切分 |
| 静默覆盖他人改动 | 校验在命令内重读文件 | 版本号跨命令传递 + 三方合并 |
| 二进制自称 1.0.0 | `Cargo.toml` 从不更新 | 跟随 git tag + CI 校验 |
| 自检三个 FAIL 来自它自己 | 硬编码、判定宽松、依赖真实数据 | 逐一改成不依赖真实数据 |
| 任意文件可被改写 | `skill decide` 的候选名直接拼进路径 | 拒绝含路径的文件名 |
| `attach add --dry-run` 照样写盘 | add/commit 没有 dry-run 分支，且 main 见 dry-run 跳过锁 | 两处都补真 dry-run |
| 5MB 附件改中间字节报"内容没变" | 指纹只读头尾；改成 16 块抽样仍有空隙 | 不再抽样，全量哈希 |
| `update` 与其它命令四处分叉 | 唯一手写自己那套写盘流程 | 改走 `save()` |
| `set` 能写入身份字段 | 通用后门没有护栏 | ID/STATUS/FORMAT 三类拒绝并指路 |
| `move` 拼错分支会新建分支 | 创建分支是副作用 | 只由 `branch add` 做 |
| `branch`/`doctor`/`refs` 不加锁 | 漏在写命令列表外 | 补入 |
| `attach --name /tmp/victim` 写到目录外 | `dir.join` 遇绝对路径替换整个前缀 | 名字必须是单个文件名 |
| `attach add --dry-run` 留下空 `-refs` 目录 | mkdir 在 dry-run 判定之前 | 目录创建移到判定之后 |
| `vault ledger --dry-run` 照样写盘 | 该路径没有 dry-run 分支 | 抽出只读 `diff_ledger()` |
| `vault verify` 看不见坏凭据 | 遍历的列表自己会静默跳过解不开的文件 | 先扫磁盘再与可解条目对账 |
| `vault verify` 对空库/读不到也报通过 | `read_dir` 的 Err 被 `if let Ok` 吞掉 | 目录不存在 rc=3、读不到 rc=6、坏文件 rc=5 |
| `list --status CANDIDATE` 报「共 0 条」 | 库归属由目录决定，该 STATUS 值不存在 | 零命中时说明条件用错了 |
| `skill lint` 对 `references/` 里的问题全返回空 | 只扫 SKILL.md 和顶层文件 | 递归全目录，逐文件套同一套判据 |
| 跨 Skill 引用检查永远返回空 | 默认根 `~/AgentSkills` 是空目录 | 用 `ABOOK_SKILLS` 指真实目录；实测能抓到 |
| 同秒同标题的两个候选仍可能互相覆盖 | 内容哈希截到低 32 位，已实测撞出 | 用全 64 位 + 落盘前比对实体内容，撞名换序号 |
| `-refs` 是符号链接时能删掉目录外文件 | `is_dir()`/`metadata()` 全程跟随链接 | 四处改 symlink_metadata + canonicalize 前缀校验 |
| 同一秒同标题的两条 skill 候选互相覆盖 | 文件名只用秒级时间戳 + slug | 加内容哈希后缀 |
| `skill lint` 对 `/tmp`、`../`、跨 Skill 名全返回空 | 判据是列举前缀和短语 | 改按形态判断 + 比对真实同级 Skill 名 |
| `skill decide` 失败但已生效 | 先改候选 STATUS 再写日志 | 顺序反过来：日志先写 |
| `attach --force` 复制失败会毁掉旧附件 | `fs::copy` 直写目标：先截断再写，失败还删残骸 | 复制到同目录临时文件，成功后 rename |
| 中断复制留下半截临时文件被当成附件 | 进程被信号杀死时清理代码没有机会执行 | scan 识别 `.名字.tmp<pid>.<纳秒>` 并删除 |

| 凭据被改一个字节，`verify` 照样 PASS | 密文是可塑加法流，无任何校验 | 写入附 MAC，解密必校验，不符即拒返回明文 |

| `state` 为两个整数解析全部 972 个文件 | `read_state` 走 `load_lib`，逐个 `fs::read`+`parse` | 只读头部 4KB 扫 STATUS，70→10ms |

## 九点六、列举法守不住边界

`skill lint` 原来只认 `/home/` 和 `C:\` 开头的绝对路径，于是 `/tmp`、`/root`
畅通无阻。改成按形态判断（`/xxx` 前面是行首或分隔符，或 `X:\`）。

跨 Skill 引用那条更典型：原来只认「参见」「见另一」「依赖其它 Skill」这些短语。
但一个 Skill 引用兄弟 Skill 时根本不会用这些词——它会直接写那个名字。现在拿
同级目录里真实存在的目录名去比对。

**边界只能由"引用了什么"决定，不能由"用了哪些措辞"决定。** 凡是我用列举法
写出来的检查，漏掉的那一条永远是我没想到的那条。

## 九点七、校验放在副作用之后 = 状态不可知

两处同型：`split` 先写盘再复读校验，`skill decide` 先改候选再写日志。失败信号
来得太晚，操作者据此判断的状态与磁盘不一致——他以为没生效，其实已生效；或者
以为生效了却没留痕迹。

规则：**任何会失败的写操作，先做最不可能失败的那部分，并且在动数据之前完成所有
校验。** 这样失败点总是落在"数据未变"或"偏差可发现"这一侧。

## 九、一条反复出错的推理

大文件指纹改了三版，每版都比上一版更像回事，但都错在同一个地方：

1. 头 64KB + 尾 64KB —— 改中间就漏
2. 16 块均匀抽样 —— 块间有空隙，落在空隙里照样漏（实测第 2500000 字节）
3. 全量哈希 —— 对

前两版的推理都是"没人会那样改"，而这条链路的失败形态是**证据已被改，工具
回答没变**。附件是记录携带的原始证据，证据坏了却报完好，比误报更坏，因为它
让人停止怀疑。空隙是数学上不可避免的：要么覆盖全部，要么留缝。

成本实测划得来：逐字节 FNV-1a 约 500MB/s，5MB 约 10ms，50MB 约 100ms。

## 九点五、源码修好 ≠ 交付修好

子代理报的一处漏洞，我在源码里已经改了，但它复现时用的是**已发布的二进制**。
两边都对——源码是修好的，用户手里那份还是坏的。中间隔着构建、安装、发布三
步，漏任何一步，"我修好了"这句话就不成立。

对账办法：`abook version` 输出的 `src=` 是编译时源码指纹，与当前源码重算的
指纹比对。不一致就说明在跑旧代码。

    ./target/release/abook version | grep -o 'src=[a-f0-9]*'

发版四步缺一不可：源码改完 → 构建 → **用 `src=` 核对二进制与源码一致** →
推送并打 tag → 等 CI 产出 15 个架构 → 下载回来自报版本与 tag 一致。

## 九点八、把"不知道"报成"没问题"

`vault verify` 漏报修了两次，第二次才修到根上。第一次是"坏文件被列表自己跳过"，
第二次是"目录读不到时 `read_dir` 的 Err 被 `if let Ok` 吞掉"。

同一段代码把三种状态折叠成同一个输出：

| 实际状态 | 应回答 | 曾经回答 |
|---|---|---|
| 库建好了、没有凭据 | 通过 | 通过 ✓ |
| 库里没建 `vault/` | 不知道，可能备份没做 | 通过 ✗ |
| `ABOOK_ROOT` / `HOME` 指错 | 在查别人的地方 | 通过 ✗ |
| 有文件但解不开 | 失败 | 通过 ✗ |

这类缺陷的共同形状是**用默认值兜住错误**：`if let Ok(x) = ...` 之后 `x` 缺席，
后续逻辑把"没拿到"当成"拿到了空的"。自检类命令尤其不能这样——它的全部价值
就是回答"我的东西还在不在"，一旦把"不知道"报成"没问题"，它比不存在更坏。

判据：任何以"检查/校验/对账"为目的的命令，`Err` 与空集必须走不同分支，且
退出码必须不同。

## 九点九、空结果是最容易被误读的答案

`list --status CANDIDATE` 输出「共 0 条」。有人会读成"候选库是空的"，于是去查
自己刚写进去的记录为什么没了；实际上 `CANDIDATE` 根本不是 STATUS 取值——库归属
由目录决定。

零命中至少有三种含义：

  ​  确实没有匹配
  ​  筛选条件不适用于这套数据模型
  ​  条件拼错了

只回一个数字，读的人分不出是哪一种，就会朝最坏的方向猜。报告空结果时要同时说明
"这个条件是什么含义"，成本只有一行。

## 九点十、检查范围小于被检查对象

`skill lint` 只扫 `SKILL.md` 和 Skill 目录的直接子文件。而 Skill 的正文本来
就可以拆到 `references/`、脚本、模板里——自包含要求覆盖整个 Skill，不是只覆盖
入口。把违规内容全塞进 `references/deep.md`，lint 返回 `problems:[]`、`ok:true`。

同一类问题还出现在别处：跨 Skill 引用检查默认去 `~/AgentSkills` 找兄弟目录，
而本机那个目录是空的，于是检查永远返回空——它不是"没发现问题"，是"没去看"。

**判据：检查命令必须先确认自己看过了什么。** 扫了 N 个文件就该报出 N，扫了 0
个文件要么报错要么明说"没有可检查的对象"，不能两者都输出"通过"。

## 九点十一、唯一性靠哈希算出来，就必须落盘前再验

候选文件名加了内容哈希防覆盖，但截到低 32 位。生日碰撞在几十万条量级就能撞，
而实测已经撞出来了：两条不同正文算出同一个值，第二条覆盖第一条，退出码 0。

改成全 64 位，并且**不把"哈希不同即路径不同"当成保证**：路径已存在时比对实体
内容，相同视为幂等，不同则换序号。

截断只是让它更容易撞，不截断也不改变"要验"这件事。凡是把唯一性交给某个计算值
的副产品，落盘前都要回到实体上再确认一次。

## 九点十二、路径拼对了，指向的地方可能不是我以为的

`-refs` 目录被做成指向 `/tmp/xxx` 的符号链接后，`attach list` 把目标目录里的
文件列成本记录的附件，`attach rm victim.txt` 回"已删除" ——删的是 `/tmp/xxx/
victim.txt`。三条命令都成功，都退出 0，而删的那个东西根本不属于这个记录。

根因不是路径拼接算错，而是全程用跟随链接的判定：`is_dir()` 为真、`metadata()`
拿到目标的大小。一个指向别处的链接，在磁盘上看起来就是一个正常目录。

四处一起改：扫描用 `symlink_metadata` 并跳过链接、目录枚举只认真实目录、删除
前 `canonicalize` 两侧比对前缀、写入前拒绝链接目录。

**判据：目录边界要在每次判定时重新确认，不能靠一次 `is_dir()`。** 凡是用
"这个名字指向的是什么"来决定行为的代码，都要问一句"它是不是指向了别处"。
删除类操作尤其如此——它是唯一不可逆的，值得多花一次 `canonicalize`。

## 九点十三、覆盖写必须走临时文件

`attach --force` 覆盖一份已有附件时，原来是 `fs::copy(src, dst)`。这个调用
**先把目标截断成 0 字节再往里写**，于是从截断那一刻起，旧内容就已经不存在了。
只要写到一半失败——磁盘满、超文件大小限制、进程被 SIGXFSZ 或 SIGKILL 杀掉、
网络盘断开——旧附件就永久没了。错误路径上还有一句 `remove_file(dst)` 清理
"半截文件"，把残骸也删干净，连抢救的余地都不留。

实测：一份 25 字节的附件，用 `ulimit -f 1` 限住文件大小，再 `--force` 覆盖
一个 1 MB 的源。进程被 SIGXFSZ 终止，目标变成 1024 字节全零，原内容消失。

**判据：任何"覆盖一个已存在的文件"的写操作，都必须先写同目录临时文件、
完整成功后再 rename。** 三条理由缺一不可：

1. `fs::copy` / `fs::write` 都不是原子的，它们的语义是"打开、截断、写"。
2. rename 在同一设备内是原子的，目标要么是完整的旧内容、要么是完整的新内容，
   不存在中间态。所以临时文件**必须与目标同目录**，跨设备 rename 会退化成
   "先删目标再复制"，正好退回我们要避免的那一步。
3. 失败时只能清临时文件。目标路径上那份旧数据与本次失败无关，不该被牵连。

`write_atomic` 早就是这个形状了，`attach place` 却手写了一套复制流程绕过了它。
这不是不知道怎么写，是有两条并行的写盘路径，而只有一条被改对了。

**推论**：进程被信号杀死时清理代码没有机会执行，所以临时文件会残留。残留物
若被当成正常文件统计（附件目录里就是如此），它会被算成"一份完整附件"，
而它其实不完整。所以扫描时要把它们识别出来删掉——判据要收窄到能确认是自己
留下的形态，不能笼统地删"看起来像临时文件"的东西。

## 九点十四、自检不能拿被测代码自己的清单

`vault verify` 原本的流程是：遍历 `list_entries()` 得到条目列表，逐个校验。
问题在于 `list_entries()` 自己就会把解不开的文件静默跳过——读失败、解密失败、
文件名不合规，都只是 `continue`。于是坏文件从一开始就不在列表里，verify 校验
完剩下的好条目，全部通过，报告"0 失败"。

**自己拿一个会藏问题的清单去查问题，结构上就不可能查出问题。** 这不是忘了
处理某种情况，而是证据来源本身就是被怀疑的对象。

改法是先扫磁盘、拿到全部文件，再逐个尝试解析，把成功的和失败的分别列出来。
坏文件必须进入视野，才有资格被报出来。

同一节还有第二个坑：解得出 ≠ 校验通过。对没有校验码的旧格式条目，原来的
`verify` 一律报 PASS，等于把"无从校验"说成了"校验通过"。这两件事必须分成
两档报，而且"整库都无从校验"时退出码不能是 0——否则脚本会把它当绿灯。

**判据：自检的判据来源必须独立于被检对象。** 问自己一句：这个检查遍历的
列表是谁产生的？如果它和被检查的东西是同一段代码，那它验的是"剩下这些没坏"，
不是"没有坏的"。

## 九点十五、只读命令必须真的只读

修"中断复制留下半截临时文件被当成附件"的时候，我把删除放进了 `scan()`。
这个函数听名字就是个读取操作，但它被 `attach list`、`attach get`、
`attach sync`、`attach edit`、`attach commit` 全都调用——于是一夜之间，
`abook attach list` 开始删文件，连 `--dry-run` 都删。

这比原来的缺陷严重得多。残留文件是看得见的：`ls` 一下就能发现，自己删掉即可。
而一个查询命令悄悄删掉磁盘上的东西，用户根本不会想到去查——他刚问了一句
"我有哪些附件"，问题就消失了。

**判据：函数名里带 list / get / show / scan / view 的，不许有副作用。**
如果确实需要周期性清理，把它放在写入路径上（那些命令本来就声明了会改库），
或者在专门命令里做。要清理的东西记进返回值，由调用方决定删不删。

顺带一条：`--dry-run` 之所以长期在 `main` 里跳过库锁，是因为它被默认为
"什么都不写"。一旦某个命令偷偷在 dry-run 里写盘，它就同时绕过了锁——
`write --dry-run` 在空目录里造出整个库骨架时，这些写入没有任何互斥保护。
预览的可信度和锁的覆盖面，是同一件事的两面。

## 九点十六、报得太多等于没报

`skill lint` 对真实库 118 个 Skill 报了 116 个、18668 处。这个检查在功能上
是"工作"的——它确实在报东西——但实际效果等于不存在：没人会读一份把所有文档
链接都标红的报告。

三个误报来源，都不是逻辑错误，而是判据选错了粒度：

- `https://` 里那个 `s:` 与 Windows 盘符 `s:/` **形态完全一样**。盘符判据必须
  限定在词首，否则每一个链接都是"Windows 绝对路径"。
- `/pua`、`/design-review` 是斜杠命令，不是路径。绝对路径至少要有两段。
- `design` 这个词在 `refactoringguru.cn/design-patterns/` 里、
  `professional` 在 `pro` 这个 Skill 名里，都会命中纯子串匹配。

**判据：一个检查的价值 = 真阳数 / 总报警数，不是真阳数。** 当误报多到让人
不再阅读时，它已经从"有帮助"变成了"有害"——因为它还会给出一个
`INTEGRITY` 退出码挡住流程。收窄判据、容许漏掉少数真问题，通常比维持
一份没人读的全量报告更有价值。

## 九点十七、补救命令必须比别的命令更不可能写坏东西

`vault rekey` 的语义是"种子泄露之后换一把新的"。它出过一个最讽刺的故障：
`encrypt_text` 返回的文本第一行**已经**是新种子，`rekey` 又在外层拼了一次
`{new_seed}\n`，于是文件开头有两个种子行。解密时首行当种子，第二个 12 位数
和正文 token 一起被摊平进去，校验码必然对不上——条目永久读不出来。
而命令报的是"已重设 2 条"，退出码 0。

也就是说：**泄露发生后的第一次补救，把整个库作废了，还告诉你成功了。**

两层教训，第二层更重要：

1. 补救类命令要走和普通写入一样的自检。`write_entry` 早就有"写完解密回读
   比对"，`rekey` 没有——不是不会写，是写的时候没想到它也算写入。
2. **越是"救命"的命令，越要假设它自己会出错。** 一条每天跑十次的查询命令
   写坏了,你当天就发现；一条三年只用一次的补救命令写坏了，等你真需要它的
   时候才发现库里已经全是坏的。所以对低频、高危命令，验证要做到比对每次
   写入都更严——这次是写完立刻 `read_entry` 复读、并逐字比对明文是否一字
   未变，任一条不符就整体报错并指明是哪一条。

顺带一个观测：我给 vault 加完整性校验（MAC）之后，这个老 bug 从"无害"变成
"毁库"。之前重复的种子行会因为 `parse::<u16>` 溢出被静默跳过，明文照样正确；
加了校验之后那行计入 MAC，就对不上了。**加校验会把潜伏的数据问题激活成
显式故障**——这既是好事（问题终于可见），也提醒我先扫一遍存量数据再加校验，
否则升级那一刻全库同时变红。

## 九点十八、性能问题往往不在算法，在一个随手写的系统调用

`abook` 变慢的头号原因不是检索算法、不是索引结构，而是这一行：

```rust
std::process::Command::new("date").arg("+%z").output()
```

它用来取本地时区偏移。没有缓存，而格式化时间戳的函数每渲染一行就调它一次。
于是**每显示一行就创建一个进程**。strace 里单次 fork 是 9 次 `execve`
（前 8 次 PATH 探测失败），2.0 毫秒。`list --per-page 500` 因此要 1.6 秒，
其中 89% 花在创建 500 个 `date` 进程上。

这个 bug 活了很久没被发现，因为**小样本看不出来**：默认 `list` 只显示 31 行，
31 × 2ms = 62ms，混在别的开销里不显眼；`search` 默认最多 30 条命中，同理。
只有把 `--per-page` 拉到 500 才会暴露成 1.6 秒。

三条可迁移的判断：

- **耗时随"输出行数"增长而不是随"数据量"增长的，先怀疑每行都有一次系统调用。**
  这跟直觉相反——通常以为慢是因为库大，但这次 `list --per-page 1` 和
  `--per-page 500` 差 10 倍，库大小完全没变。
- **"取一个常量"却用了外部命令。** 时区偏移在进程生命周期内是恒定的，
  标准库又有 `OnceLock`，一行缓存就能覆盖七条命令。凡是"值不变但每次都重新
  获取"的地方都值得看一眼。
- **测性能要用微秒计时。** GNU `time -f %e` 只有 10 毫秒精度，1 毫秒级的差异
  完全看不出来，而这类"每行 2 毫秒"的 bug 恰好在那个量级。

第二项 `state` 的问题更朴素：它只需要"非 DELETED 的记录数",却调 `load_lib`
把 972 个文件逐个 `fs::read` + `Record::parse`，实测 1010 次 `openat`、
6740 次 `statx`，只为了得到两个整数。**要一个字段，就只读那个字段**——判
DELETED 不需要正文、不需要字段表、不需要任何克隆，读前 4KB 扫一遍头部即可。

顺带纠正一个我自己的猜测：我原本以为 `state` 慢是因为做了全量哈希。查下来
**它从来没做过哈希**，sha256 只在写入路径和 vault 用。真正浪费的是解析与
克隆。凭直觉猜性能热点，十次里有几次会猜错方向。

## 十、另一种假动作

`attach add --dry-run` 曾经真的复制文件、回写清单、刷新 UPDATED、写 commit，
而且因为 `main` 见 `--dry-run` 就跳过库锁，它还是在**无锁**状态下改库。

比没有这个开关更坏：一个叫"只看看会发生什么"的开关做了真事，用的人从此不会
再相信 dry-run。凡是有 `--dry-run` 的命令，其分支必须在任何写盘之前返回，这
一条应该由自检覆盖而不是靠自觉。

## 十一、把"等价替换"当成事实，没有验证

为了让每行少一次内存分配，`grep` 把行的小写化从 `str::to_lowercase` 换成
`chars().flat_map(char::to_lowercase)`，注释里还写了一句"这正是标准库内部做的"。

那句话是错的，而它错得几乎看不出来。标准库对小写化是**上下文相关**的：希腊
字母的词尾 `Σ` 映射成 `ς`，其余位置映射成 `σ`；而按字符逐个映射永远给出 `σ`。
于是 `ΣΟΦΟΣ` 在旧代码里折叠成 `σοφος`，在新写法里变成 `σοφοσ`，搜 `ς` 或搜
`σοφος` 都再也找不到那条记录。

**命中的丢失是完全静默的**：命令退出码 0，输出格式正常，只是少一行。这类缺陷
不会有人报 bug，因为没人知道自己漏了什么。

三条教训：

1. **"这两个写法等价"是一个需要证明的断言**，不是可以顺手写进注释的感想。
   尤其涉及 Unicode、大小写、排序、路径规范化这些有大量特例的地方。
2. 一旦把某个库函数替换成手写实现，**验证方式必须是对拍**：同一份输入分别
   喂给两个版本，逐字节比对输出。我这次是靠造一条含 `ΣΟΦΟΣ` 的记录、比对
   `grep ς` 的行数（3 对 1）才发现的。
3. 这次替换的**收益本来不存在**：`grep` 的时间几乎全在加载全库——`list --q`
   加载同样两个库且不输出任何行，耗时与 `grep` 相同（约 108 ms）。为一个不存在
   的收益冒损失真实命中的风险，是纯粹的自找麻烦。

顺带记下实测没收益但保留的改动：`read_str` 改用 `String::from_utf8` 接管字节
缓冲，能省掉一次整文件复制，但 40 MB 记录的 `cat` 峰值 RSS 旧 196 MB、新 198 MB，
差异在噪声内——峰值出现在解析阶段的多次 clone，那份复制在解析完就释放了。所以
这条记作"消掉一处冗余复制"，不记作性能优化。**不要在提交信息里把清理写成优化。**

## 十二、把"能读整份"当成"必须读整份"

选择器回退到标题匹配时，代码用 `read_head` 只取前 4 KiB，却把这 4 KiB 原样
交给 `parse`。`parse` 要的是**完整文档**——它靠 `[/CANONICAL_MEMORY]` 这类闭合
标签判断正文在哪结束。拿到一段被截断的前缀，它就把剩下的残段当成正文，全部
走一遍解析流程；而调用方只想要一个 `TITLE`。

修法是在首个 `[` 行处截断，再补一个合成的闭合标签。但**这个改动只有在证明
"截掉的部分不影响结果"之后才能做**：

实测全库 964 条记录，没有任何一条的 `TITLE=` 出现在这种 `[` 标记之后，也没有
任何一条在 4 KiB 内缺 `TITLE=`。有了这条事实，截断才是等价的。

效果比预期大：未命中查询 97 → 49 ms，标题前缀 55 → 29 ms。因为"读头部"省的是
I/O（早已省了），而"解析整篇"省的是 CPU——后者才是大头。

两条可迁移的判断：

1. **函数名里的"头"只约束了输入，没约束下游怎么用它。** `read_head` 拿到的确实
   是头部，但把它传给一个期待完整文档的函数，头部的优势就没了。
2. **等价性要用数据证明，不是用接口相似推断。** 我先跑了上面那条全库检查才动
   手；如果只是觉得"头部够用了"，正好漏在"某条记录的 TITLE 写在附件块后面"
   这种边界上。

顺带：这次对拍用了 1500 个选择器（完整文件名、哈希后缀、ID、标题全名、标题
前缀五类），逐条比对 `get` 的完整输出与退出码。选择器矩阵比手工挑几个用例可靠得多。

## 十三、给列表加元信息：三条命令各写一套，读者就要认三次列

`list` 很早就是每条记录都带 `时间 体积 行数`。但那不是规范，只是它自己的实现
——`path` 写成 `体积 行数 时间`（顺序不同），而 `index`/`branch`/`recent`/
`history`/`skill`/`vault` 一样都没有。

单看每一条命令都没错：它们各自在回答各自的问题。问题出在读者身上——同一个人
在同一个库上来回换命令，每换一条就得重新认一次"这一列是什么、单位是什么、缺失
的时候是空还是零"。

统一的产物是 `util::row_meta(when, bytes, lines)`，八条命令共用一处实现。三条
设计判断：

1. **缺席的维度写 `-`，不写空、不写 0。** `vault ls` 的契约是"不解值"，所以它
   算不出明文行数。留空会被读成"这条没有行数这回事"，写 0 会被读成"这个条目
   是空的"——后者是对数据的错误陈述。`-` 只说一件事：这一维度在此不可得。
2. **元信息必须是同一份数据，不是各算一遍。** `index` 的文本输出与 `--json`
   必须给同样的 `bytes`/`lines`/`updated`；否则"要不要读这一条"在人和机器两侧
   的依据不同，机器侧只能盲取。实现上把元信息计算提前到 `if json` 之前，两个
   分支共用。
3. **缺席字段的类型要能被脚本区分。** JSON 里补了 `kind`(branch/record) 和
   `status`(both/canonical/candidate)。原先调用方只能靠 path 里有没有
   `/records/` 去猜类别——那是字符串形状的巧合，不是契约，改一次命名就崩。

聚合口径也必须一致：分支的 `bytes`/`lines` 按 basename 去重后求和，与 `tree`、
`branch` 同一算法。三个命令看同一个分支，给出的数字必须一样，否则读者会开始
怀疑是哪一个在骗他。

## 十四、预载视图要建立印象，而不是报健康

原来的记忆预载入口是 `state`：312 字节，报记录数、收录时刻、一致性。它回答的
是"库有没有坏"——这个问题在写入前和报健康时才需要问。

但"开工第一条命令该看什么"是另一个问题：**这个库里大概有什么、我该往哪个方向
查、手上有什么牌**。`state` 一个字都不答。

`index` 现在承担这件事：分支行给条目数/体积/行数/最近活跃与 READ_WHEN（"什么
时候该翻它"），正式记录与未晋升候选分两段，末尾接凭据段。总输出 4.5 KB，1 万字
左右，在预载预算内。

三条设计判断：

1. **候选必须单独成段并标明证据地位。** 候选与正式记录并列在 `Index.md` 里，
   但可用性完全不同：正式库是已闭合、经用户批准的结论；候选是"可能还有矛盾、
   还没验证"的材料。混在一张表里打印，读者会把候选当同等可靠的依据。但也**不能
   不列**——不列就等于让调用方完全看不见手上还有什么线索。做法是列出并明确写
   "不可当结论"。
2. **凭据段是最容易漏的那一段。** 记忆里记着某个系统的排障方法，但没人提醒
   "你还存着它的账号"，于是调用方只会去查资料、不会想到直接去验证。索引回答的
   是"我手上有什么牌"，凭据正是最容易忘掉的一类。只给标识与用途，永不打印值。
3. **预载视图本身不能贵。** 元信息最初走 `load_lib`（全解析 964 条），实测 80 ms；
   而索引只需要字节数和行数，不需要任何字段语义。改成原始读+数行后 6 ms、纯 stat
   1 ms，整条命令 0.02 s。**在预载路径上的第一条命令，贵一倍都是设计错误。**

## 十五、把分发流程写进文档，等于每轮重走一遍并指望没人记错

此前"下载新版本并装好"是一段写给 AI 读的规范：判断系统与架构、在 PATH 里挑
用户级目录、按序试五个下载源、验五条、原子替换。它每个字都对，但它要求每一轮
都重新执行一遍这七八步，而任何一步记错的表现都是**装了个坏二进制还报成功**。

现在收进 `abook upgrade`。五条设计判断：

1. **替换的是 `current_exe()`，不是硬编码路径。** 二进制可能被装在 PATH 上任何
   一个目录。猜安装位置会在升级时写出一份影子副本，让机器上出现两个版本、哪个
   生效取决于 PATH 顺序。
2. **先取 manifest，再决定要不要下 1.6 MB。** manifest 带 `sha256` 与 `version`，
   能在下载之前回答"已经是最新"；没有它，每次检查都白下一份完整二进制。
3. **下来要过三道，任一不过就回滚。** 校 `sha256` → 让新文件自报版本并与
   manifest 比对 → 跑它自己的 `selftest`。只验"名字对了"不足以保证它在这个
   架构上真能跑。装完不跑自检的升级，等于把验证责任推给用户。
4. **版本比较必须按数字段。** 字符串比较会把 `1.6.9` 判成比 `1.6.15` 新，而
   表现是"永远说已是最新"，没有任何报错可循。`ver_tuple` 切段比较，并有单测
   钉住这个顺序。
5. **`--url` 要同时作用于 manifest 与文件。** 只作用一半会出现"文件从镜像取、
   manifest 从 GitHub 取"，而镜像存在的理由恰恰是 GitHub 不通。裸路径当本地
   目录——内网共享盘与离线机都用得上。

镜像顺序：GitHub 直连 → 三个前缀代理 → jsDelivr。五个地址都实测可达（jsDelivr
的 Range 请求不支持，这不影响整文件下载）。

## 十六、用例通过不代表用例在检查

分页核对用的测试库，`Index.md` 写的是 `| 主题 | 位置｜` 且没有
`[MEMORY_CONTENT]` 标记。而 `routes()` 只认表头含 `BRANCH`/`分支` 的表格，
`BookFile::load` 只取 `[MEMORY_CONTENT]` 与 `[/MEMORY_CONTENT]` 之间的内容。

两处都不对，于是这个测试库**从建成起就解析出零条路由**，`index` 只打一行标题。
分页核对在"没有行可翻"的数据上永远通过——它测的是数据，不是代码。

它一直被当成 PASS，直到 `index` 多输出了两行（凭据段），把总行数推过测试的
3 行门槛，才暴露出"声明了分页但分页不生效"。

这和第 427 行那条（自检不能拿被测代码自己的清单）是同一个病的两种形态：

- 那条是**被测对象提供的答案**被当成检查依据；
- 这条是**夹具太小或格式不对**，让检查条件永远成立。

识别方法：问这个用例在什么情况下会失败。如果答不上来，它就不是检查，是一个
恰好通过的语句。分页用例的正确答案是"夹具必须有足够多的行"，那就得让夹具真的
写对格式、真的产生行——而不是让它永远是一行。

## 十七、越界分支写反：不是错结果，是挂死

`merge::diff` 里 `while i < a.len() || j < b.len()`，两个越界分支的极性写反了：
`a` 用完只剩插入（要 `j` 前进），却给了"`i` 前进"的取值；`b` 用完只剩删除
（要 `i` 前进），给的又是相反的一支。于是 `i` 越界后继续自增、`j` 停在原地，
循环条件恒真——挂死。

触发条件很普通：任一版本在末尾多一行（追加）就走这条路径。所以两个用例挂死，
而"两版行数相同"的另外三个用例都能通过。**死循环被用例规模掩盖了**：三行对三行
的用例永远走不到越界分支。

该模块当时没有调用方（三方合并的基础件，尚未接入改记录的路径），所以它不影响
任何命令的行为。这一点很容易让人做出"先放着"的判断——但它让整个 `cargo test`
挂住，等于把测试套件废掉。一条挂死的测试比一条失败的测试更有害：失败会告诉你
哪里错了，挂死只让你不再运行测试。

两条可迁移的判断：

1. **差异算法的用例必须覆盖"一侧更长"和"一侧更短"。** 等长用例只能验证替换，
   验证不了插入与删除的边界。
2. **没有调用方的代码同样要能跑通测试。** "反正没在用"不是不修的理由，因为 CI
   与本地测试是整体跑的。

## 十八、把一种排版当成格式：同一份 JSON 换个工具打印就不认

`upgrade` 解析 manifest 时用了三处字符串查找：`"target":"<triple>"` 找条目、
`"sha256":"` 取字段、`"version":"` 取版本号。三处都把冒号两侧的空白写死成了
"没有空格"。

CI 生成的 manifest 恰好是紧凑写法，所以它们一直工作。任何人用 `jq`、
`python3 -m json.tool` 或 `json.dumps` 重新格式化（冒号后多一个空格），三处
全部落空。

**真正的损害不是解析失败，是报错方向指错**：

- 条目查找失败说成"里面没有 x86_64-unknown-linux-musl"——把 JSON 解析问题
  说成了"这个源没有你要的架构"。
- 版本查找失败说成"manifest 未声明版本"——把解析问题说成了"这个源太老"。

于是排查方向被引到"我是不是下错源了""是不是这个镜像没同步"，而真正的原因
是解析器不认这种写法。**报错指向错误的地方，比不报错更费时间**，因为它让人
去查一个不存在的问题。

三处一起修，因为改一处漏另一处时表现还不一样（一个是"没有该架构"，一个是
"未声明版本"）——这类"同一个错误原因在不同代码路径上有不同症状"的情况，
必须一起改并一起测。

顺带记一条更一般的判断：**解析 JSON 就按 JSON 的语义解析，不要假设某个脚本
拼出来的字符串形状。** "它现在长这样"不等于"它只能是这个样子"。

## 十九、显式指定了源还悄悄换源，等于把验证做废

`abook upgrade --url <镜像>` 原本的实现是：把 `--url` 插到回退链最前面，然后
继续走 GitHub → 三个代理 → jsDelivr。

于是内网镜像不可达时，GitHub 接上并成功，最终打印"已是最新"。屏幕上只有一行
"不可达"紧跟一个成功结论，没有任何提示说源被换掉了。

这不是"回退"这个设计错了——默认情况下回退是必要的。错的是**在用户显式指定源
时也回退**。用户给 `--url` 的场景恰恰是"我要确认这个源能用"：内网镜像、离线
机器、公司代理。此时悄悄换源，等于让验证永远通过，且永远验证的是另一个东西。

**验证的意义就是确认那个源能用，悄悄换源等于把验证做废。**

修法：给了 `--url` 就只用它，失败即 BLOCKED（退 4），并在提示语里写明"指定了
`--url` 只认这个源，不会回退到公网"。另外提示语要按 `explicit` 分叉——显式源
的失败提示里不该再建议"试试直接指定镜像"，那正是他已经做过的事。

## 二十、同一个管道陷阱踩两次：`cmd | tail` 之后的 `$?` 是谁的

复核 `--url` 不可达的退出码时，我写的是 `abook upgrade --url /nonexist | tail -6;
echo "RC=$?"`，得到 0，据此判断"失败路径退 0 是个缺陷"。

实际返回 4。`$?` 拿到的是 `tail` 的退出码，而 `tail` 永远成功。

这个陷阱在本文档里已经记过一次（"[...] 版本输出走 stderr；`grep -o` 在页脚
匹配两次"那一带的测试脚本假象），这次又踩了。所以把它记成规矩：

**凡是要判断退出码，一律先重定向到文件再单独取 `$?`**：

```sh
cmd > /tmp/out 2>&1; rc=$?; tail -6 /tmp/out; echo "rc=$rc"
```

不接管道，不接 `&&`，不接 `$(...)`。代价是多写一行，收益是结论不会反。

更一般地说：**测量工具本身也会错**。当一次测量得出"这里有严重缺陷"这种结论时，
先怀疑测量——尤其当这个结论会让人去改一段本来正确的代码。

## 二十一、检查器没报错，先确认注入真的生效了

写 `scripts/check-workflow.sh` 之后我第一次验证它：注入一处"多两格缩进"，
运行检查器，报 0 处错误。

差一点就把这当成"检查器正常"了——那是反向结论：真实事故就是缩进错误，检查器
却报 0 错误，说明它根本没在检查。

原因是注入本身没生效：我按 10 空格缩进去匹配，而那行早已在上一轮修复中变成
14 空格（它在 `if` 块里）。替换静默落空，文件没变，检查器自然报 0。

**"注入失败 + 检查器正常"和"注入成功 + 检查器有效"在屏幕上长得一模一样，都是
0 处错误。**

所以验证检查器必须固定三步：

1. 注入后先 `diff` 或断言，确认文件真的变了；
2. 再跑检查器，期望它报错；
3. 恢复后再跑一次，期望它回 0。

只做第 2 步的"验证"是自欺。后来我对三类错误（多缩进、缺右括号、shell 未闭合
`if`）都按这三步做，才敢说检查器有效。

这条和第十六节（用例通过不代表用例在检查）是同一个病的两面：那一节是**夹具
太小**让检查永远成立，这一节是**注入没生效**让检查永远成立。共同点都是"检查
在跑，但没检查到东西"。

## 二十二、抬头数字与实际行数不符，读者会怀疑整张表

`index` 的抬头原本是：

```rust
println!("Index.md  路由 {} 条（分支 {} / 记录 {}）",
    routes.len(), branch_agg.len(), rec_rows.len());
```

三个数字里前两个取的不是"实际要打印的行"：`routes.len()` 是 Index.md 解析出的
路由总数（与实际打印无关）；`branch_agg.len()` 是 Atlas 聚合表的条目数，而那份表
里存在没有对应 Index.md 路由的分支。

真实库上直接现形：抬头写"路由 26 条（分支 20 / 记录 7）"，而 20+7=27、实际印出
19 行分支 + 7 行记录。三个数字两两都对不上。

危害不是"数字不好看"。**抬头是读者最先会去数的地方，数一次对不上，后面每一个
数字都会被怀疑**——哪怕它们都是对的。一个表格的可信度是从第一行建立的。

修法：三个数都取自 `br_rows.len()` / `rec_rows.len()`，总数用两者之和，不再从
另一个来源取。同时修了带过滤时的同类问题（过滤后行数变了、抬头不变）。

两条可迁移的判断：

1. **抬头里的统计量必须与正文同源。** 只要是"再算一遍"，就一定会漂移，因为它
   算的是另一个东西。
2. **能被读者当场验算的数字，错了就是在自证不可信。** 这类数字比藏在日志深处的
   统计危险得多。

## 二十三、CDN 缓存让"检查更新"在五分钟内说谎

`raw.githubusercontent.com` 带 `cache-control: max-age=300`。推完 tag 立刻跑
`abook upgrade --check`，取到的是五分钟前的旧 manifest：

```
取 manifest ← GitHub ... 15 条,本平台 1656104 字节
已是最新 (1.6.19)
```

而当时远端已经是 1.6.20 的产物（字节数也已经变了）。响应头 `x-cache: HIT`、
`source-age: 247` 说明了原因。

试过三种缓存穿透都无效（查询串 `?t=<时间戳>`、`Cache-Control: no-cache`、
`Pragma: no-cache`）——`raw.githubusercontent.com` 不吃这些，它按 CDN 边缘节点
的 TTL 走。

所以这是**发布流程**的约束，不是代码缺陷：**打完 tag 到能以"已是最新"验证之间
有最多五分钟窗口**。在这个窗口里：

- `upgrade --check` 说"已是最新"是**可能错的**；
- 但它说"有新版本"一定是真的（旧缓存里不可能出现未来的版本号）。

判断方向不对称，这决定了该怎么用：**"有新版本"可以直接信，"已是最新"要等
五分钟再用它下结论。** 若必须立刻确认，去查 `downloads` 分支的 commit（git 协议
不走这条 CDN），或直接比对 `manifest.json` 的 sha256 与本地文件。

顺带记一条：`x-cache: HIT` 与 `source-age` 这两个响应头是判断"拿到的是新是旧"的
唯一线索。看到 `source-age` 接近 300 就该怀疑，而不是等它自己过期。

## 二十四、标注太多等于没有标注

`branch` 对每个分支打印 `COUNT` 声明值与实际条数的比对。`COUNT` 缺失时它报
"未声明 COUNT"，而真实库 20 个分支**一个都没写**——`COUNT` 是 `recount` 才补的
可选冗余字段。

结果是一张每行都带标注的表。标注一旦出现在每一行，它就退化成装饰，读者会训练
自己忽略它——然后真正的告警也被一起忽略。

改法：只保留"写了但对不上"这一种。那才是地图与磁盘真漂移，或者有人手改过。

**判据**：一条提示如果对绝大多数行都成立，它就不是提示，是背景噪声。要么改成
只在违反时出现，要么删掉。

## 二十五、空列看起来像排版坏了

`list` 无条件打印 12 字符宽的附件列。库里绝大多数记录没有附件，于是每一行都是
一段空白。

宽表格里"空列"与"字段缺失"在视觉上无法区分。读者看到一片空白，第一反应是
"工具排版坏了"或"是不是有字段没填"，而不是"这批记录没有附件"。

改法：只有真有附件时才占这一列。

注意这一条与"未知维度打 `-`"不冲突：`-` 是**单个字符的显式占位**，说的是"这个
维度不可得"；而一个 12 字符的空列什么都不说。两者的区别是"有没有传达信息"。

## 二十六、永远无法通过的检查，等价于把规则废掉

`skill lint` 对超过 100 行的文件报"须在头部给出它的目录"。实现只做了前半句：
数一下行数，超了就推一条不通过——**从不检查目录在不在**。

后果：按规则补完目录，照样报。于是这条规则在实践中只有两个走向——要么人开始
无视这条报告的整份输出（真问题一起被忽略），要么人干脆不写目录（反正写了也报）。

实测在 `merge-modem-temp-patch` 上验证修好没有：补目录前 `record_preflight_test.sh`
报，补完放行；另两个文件确实没写目录，补上后也放行。**检查的判据必须与规则的
措辞对齐**——规则说的是"要给目录"，检查就得去看目录。

三种目录写法都认（真实 Skill 里都出现过）：标题带「目录」/TOC、按行号定位
（`L28 xxx`、`L28-40 xxx`）、Markdown 锚点（`](#yyy)`）。只看前 40 行——目录是给
"要不要往下读、从哪开始读"用的，塞在文件中间就失去意义。

**同类**：任何"因为 X 所以不通过"的检查，都要问一句"X 是原因还是结果"。
这里 X（超 100 行）是触发条件，不是违规本身。

## 二十七、"读得到但没人写"，是比不存在更难发现的问题

`abook identity` 从 Global.md 的 `Credential Identity Index` 读凭据清单。这条读取路径
一直工作正常——问题在于**没有任何命令写这一节**，真实库里连节标题都不存在。

于是它稳定地输出"索引为空"。这句话有两个可能的含义：

1. 库里确实没有凭据 —— 正常。
2. 索引从来没被生成过 —— 功能坏了。

同一句话覆盖这两种状态，而第 2 种更难被发现：文件、命令、代码都没报错。
只有当你明知道用户刚存过凭据、它却还说"空"时，才会察觉。

**判据**：一条读取路径如果有对应输出，必须问一句"谁写它"。写者不存在时，
读取不会失败——它会安静地返回空，而空是一个合法答案。

这次的实际损失是"有 key 但模型不知道"：保险箱里存着邮箱授权码，模型仍然会来问
用户"发邮件怎么配 SMTP"。能力在，但不可见，等于没有。

**做法**：让写入侧维护投影（`vault put`/`rm` → `sync_identity`），并且：

- 投影写失败不能回滚正本。凭据已落盘并复读校验，那是不可丢的；索引下次再试。
- 写投影的字段要能被读取侧解析回来，并且**压平换行**——解析器丢弃字段数不足的行，
  多行用途会让那条凭据从索引里静默消失。两条单测钉住这一点。
- 旧库缺节时追加，而不是报"结构不对"。
