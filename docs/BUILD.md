# 多架构构建与发布一致性

15 个目标架构，全部从同一份源码编译。这不是洁癖：提示词里的下载地址是固定的，
用户按自己的平台取文件，如果某个平台停在几个月前的构建上，不会有任何征兆。

## 一条命令产出全部

```sh
sh build-all.sh      # 本机能编的编掉，其余列出交给 CI
sh verify-release.sh # 校验产物齐全且同源
```

`build-all.sh` 逐 target 判定：

- 本机有**有效 std**（`libstd-*.rlib` 真实存在）→ 直接 `cargo build --release --target`
- 没有 → 记入「需 CI 构建」，不是失败

判据必须是「有没有 libstd rlib」而不是「target 目录在不在」：本机三个 android target
的目录都存在，里面一个 rlib 都没有，rustc 随后报 `crate std required to be available
in rlib format`——那是空壳 std，不是代码坏了。把空壳当失败会让人去查一个不存在的 bug。

## 同源性怎么证明

`build.rs` 把所有 `src/**/*.rs` 的 FNV-1a 指纹（路径 + 字节，排序后累加）编进二进制，
`abook version` 会打印 `src=<16位十六进制>`。这个值与架构无关，所以：

> 15 个文件里出现同一个指纹串 = 它们来自同一份源码。

`verify-release.sh` 用 `grep -F` 定点匹配，**不执行目标文件**——15 个里有 Windows、
macOS、异架构，在这台机器上根本跑不起来，非要执行就等于永远验不了它们。

## 期望值不能盲目相信产物

期望指纹取自本机那个能跑的二进制，但那个二进制本身也可能落后于源码。此时它会把
**新的**产物判成「不同源」，方向正好反了。

两种判据都试过，都不行：

| 判据 | 问题 |
|---|---|
| mtime | `touch` 一下内容没变，指纹也不变，却会误报 |
| `git status` | 改了又重编是完全正常的流程，会一直误报 |

最终做法是**当场重算**：脚本里照 `build.rs` 的算法把工作树重算一遍，与产物报告的值比。
不等就说明产物落后于源码，先重编。

这确实复制了一份 FNV 实现，是权衡而非疏忽：不复制就只能用上面两种会持续误报的判据，
而一个总在喊狼来了的校验，喊久了就没人看它的结论。代价是两份实现必须一起改——
一旦 `build.rs` 换了算法，脚本会立刻把所有产物报成「落后于源码」，是响亮的失败，
不是安静的漏检。

## 三个场景的实际结果

| 场景 | 期望 |
|---|---|
| 改源码、不重编 | 报「探针产物落后于源码」，退出 1 |
| 改完再重编 | 放行 |
| `touch` 但内容没变 | 放行 |

## CI 里的三道闸

发布前依次：

1. **Check all targets are present** —— 数量必须 15。少一个就中止，避免「发出去的
   版本少一个平台」这种隐形缺口。
2. **校验 15 个产物同源** —— 数量对了不等于内容对了。某个平台完全可能留着上一轮的
   旧二进制，其余 14 个是新的；文件数齐整，实际有一个平台在跑几个月前的代码。
3. **Prune stale assets** —— 删掉本轮不再产出的历史资产，避免旧文件永远挂在发布页。

顺序不能换：先确认齐全，再确认同源，最后才动发布页。

## 本地改完源码的标准动作

```sh
cargo build --release                 # 本机架构
sh build-all.sh                       # 能编的都编
cp target/release/abook "$PREFIX/bin/abook"
abook selftest                        # 必须 140 通过 / 0 失败
sh verify-release.sh                  # 确认没有陈旧产物
```

少了最后一步，`target/aarch64-linux-android/release/abook` 这类产物会一直停在上一次
成功构建的版本上，而它看起来没有任何异常。


## 以哪一份为准：远程

发布流程一次构建 15 个架构，本机架构只是其中之一，其余 14 个只存在于远程。
**所以远程那份才是权威构建。**

本机编完后要跟远程核对，并以远程为准替换本地安装：

```sh
sh sync-from-remote.sh --check   # 只比对
sh sync-from-remote.sh           # 取回并安装
```

取回后先验文件头（HTTP 200 不算成功，劫持页也是 200），再跑 `version` 确认架构对得上，
最后原子替换（临时文件放目标同目录，跨文件系统 rename 会失败）并 `selftest`。

**禁止反向：让远程对齐本地。** 本机只能编一个架构，做不到这件事。

也**不要以为源码指纹相同就字节相同**：指纹只证明来自同一份源码，工具链版本与构建环境
差异仍会让字节不同。实测同一提交下本地 1,105,648 B、CI 1,108,752 B，差 3,104 B。
以哪一份为准必须明确 —— 用户下载到的是远程那份，所以答案只能是远程。

### 源顺序与冷启动不同

`sync-from-remote.sh` 把 `raw.githubusercontent.com` 排第一，jsDelivr 排最后。

提示词里的冷启动源顺序是为**国内被墙用户**设计的，镜像优先。而这个脚本是**编完跟远程
对账**，正确性优先于可达性：jsDelivr 会对 `@downloads` 分支做长时间缓存，实测取回的是
上一版的旧文件，指纹对不上。raw 每次 force push 后立即可读。

两个场景需求不同，顺序就该不同，不是谁抄谁。
