# 容错规则表

这份文档回答一个问题：AI 写出来的记忆文件格式不对时，`abook` 到底怎么处理。

分三类：

- **吸收（Fixed）**——格式确实偏了，工具自动纠正后照常读写，不报错。
- **可读但有损（Warn）**——能读出来，但某项质量下降或存在歧义，记录位置供人判断。
- **不可用（Error）**——这个文件已经不是记录，工具不猜，明确报错。

每条规则都有固定的编号。跑 `abook check`、`abook audit`、`abook doctor` 时看到的编号就是下表的编号，可以对照查询。工具从不静默跳过任何一条——**每个偏离都会留下「哪条规则触发、原文是什么、做了什么处理」三项记录**。

---

## 一、编码与换行（N 系列）

| 编号 | 现象 | 处理 |
|---|---|---|
| N001 | 文件开头有 UTF-8 BOM | 剥离 BOM，按普通文本解析 |
| N002 | 使用 CRLF 或 CR 换行 | 统一按 LF 处理 |

Windows 编辑器、复制粘贴、脚本生成的文件常带这两项，均透明吸收。

---

## 二、结构标签（T 系列）

记忆文件用 `[MEMORY_HEADER]` / `[/MEMORY_HEADER]` / `[MEMORY_BODY]` / `[/MEMORY_BODY]` 这类标记划分段落。标签识别是宽松的：**方括号可省、大小写不限、前后空格不限、全角方括号也认**。

| 编号 | 现象 | 处理 |
|---|---|---|
| T001 | 标签缺方括号（如 `MEMORY_HEADER`） | 按标签识别，附注一条 |
| T002 | 只有闭合标签，没有开启标签 | 把闭合标签当作开启标签用 |
| T003 | 完全没有头部标签 | 从第一个 `KEY=value` 行起推断头部范围 |
| T004 | 头部标签未闭合 | 以正文起始标签为界 |
| T005 | 正文标签未闭合 | 取到文件末尾（或晋升段之前） |
| T006 | 缺少正文标签 | 头部之后全文视为正文；结构标签与晋升段会先被排除，不会被吃进正文 |
| T007 | 晋升段未闭合 | 取到文件末尾 |
| T008 | 正文里出现了标签字面量 | 按**最后一个**闭合标签截取，避免正文中途被吞掉 |
| T009 | 正文之后又出现多余的头部闭合标签 | 忽略多余的 |
| T010 | 头部标签**之前**有字段行 | 向后吸收这些行并入头部（否则记录自己的 `ID` 会读成空） |

T008 是刻意反直觉的一条：如果一个记录的正文里讨论了 `[/MEMORY_BODY]` 这串字（比如本文这种文档），按**第一个**闭合标签截取会把正文砍掉一半。所以取最后一个。

---

## 三、字段与键名（K 系列）

这是整个库最不稳定的地方：字段顺序有 65 种不同排列，一行里塞多个字段是主要写法（1581 行如此），键名拼写五花八门。**按位置解析必然出错，所以一律按键名查找。**

### 键名归一

写入前先做归一，以下替换都自动发生：

- 键内的 `-`、空格、`.`、`·` 一律视为 `_`
- 小写转大写，首尾 `_` 去掉，连续 `__` 压成一个
- 常见异拼映射到标准名

| 可能的写法 | 归一为 |
|---|---|
| `READWHEN` `WHEN_TO_READ` `WHEN` | `READ_WHEN` |
| `NOTFOR` `NOT_APPLICABLE` `EXCLUDE` | `NOT_FOR` |
| `NEXTVALIDATION` `VALIDATE_NEXT` | `NEXT_VALIDATION` |
| `RELATEDIDS` `RELATED` `REFS` | `RELATED_IDS` |
| `PREVIOUSID` `PREV` | `PREVIOUS_ID` |
| `PROMOTEDFROM` / `PROMOTEDAT` / `PROMOTEDTO` | 对应下划线形式 |
| `SUPERSEDE` `REPLACES` | `SUPERSEDES` |
| `CONCEPT` `TOPICS` | `CONCEPTS` |
| `ENTITY` | `ENTITIES` |
| `SEQ` `ORDER` | `SEQUENCE` |
| `ABSTRACT` `DESC` | `SUMMARY` |
| `MATURE` | `MATURITY` |
| `AUTH` | `AUTHORITY` |
| `PROOF` | `EVIDENCE` |
| `UNKNOWN` | `UNCERTAINTY` |
| `SRC` `ORIGIN` | `SOURCE` |
| `STATE` | `STATUS` |
| `SECTION` | `SECTIONS` |

| 编号 | 现象 | 处理 |
|---|---|---|
| K003 | 键名用了异拼或大小写不一 | 归一为标准名，记录原拼写 |
| K004 | 某行不是 `KEY=value`，是上一字段的续接 | 接到上一字段值后面（换行连接） |
| K005 | 头部内出现无法归属的行 | 忽略，但记录原文 |
| K006 | 同一字段出现两次且值相同 | 去重 |
| K007 | 同一字段出现两次且值不同 | 保留第一个值，记录第二个值供人工判断 |

### 分隔符的硬规则

- **全角顿号 `；` 永远不是字段分隔符。** 全库出现 5170 次（头部区间内 2841 次），一次都没当过分隔符，全是正常中文标点。
- **半角 `;` 只有后面紧跟 `^[A-Z][A-Z0-9_]*=` 时才分隔。** 也就是说 `EVIDENCE=甲;乙;丙` 是一个值，`ID=x;TITLE=y` 是两个字段。
- **键名必须是 ASCII 大写字母开头。** 中文键（如 `注意=`）只可能出现在正文，接受它会带来实际损害：曾有一行 `EVIDENCE=...;围栏18=18;符号定义265=...` 被解析成三个凭空发明的字段，同时真实的 `EVIDENCE` 被截断。全库 8271 个头部键行里，键名不合这条规则的为 0 个；少数非 ASCII 开头的行是孤立的续行，现在被识别为续行（K004）而不是被伪造成字段。
- **半角 `;` 与全角 `；` 的区分是硬性的**，不因「看起来像」而互相替代。

---

## 四、记录级可用性（R 系列）

| 编号 | 现象 | 处理 |
|---|---|---|
| R001 | 一个可识别字段都没有 | **不可解析** |
| R002 | 既没有正文也没有标题 | **不可解析** |

这两条是仅有的两条 Error 级规则。其余所有偏离都能读出东西来。

---

## 五、字段内容校验（S 系列）

`abook check` 与写入前校验共用这套规则。

| 编号 | 级别 | 字段 | 检查内容 |
|---|---|---|---|
| S002 | **不可用** | ID / TITLE | 缺标识性必填字段，记录无法被可靠识别 |
| S003 | 可读有损 | FORMAT / KIND / MATURITY / AUTHORITY / SUMMARY / READ_WHEN / NOT_FOR | 缺元数据字段（记录仍可读，召回质量下降） |
| S004 | **不可用** | KEYS | 既没 `KEYS` 也没 `CONCEPTS`，无法建立检索入口 |
| S005 | 可读有损 | KEYS | 缺 `KEYS`，但可由 `CONCEPTS` 派生 |
| S010 | 可读有损 | KIND | 不在枚举内 |
| S011 | 可读有损 | MATURITY | 不在枚举内 |
| S012 | 可读有损 | AUTHORITY | 不在枚举内 |
| S013 | 可读有损 | STATUS | 正式记录缺 STATUS |
| S014 | 可读有损 | STATUS | 不在枚举内 |
| S015 | 可读有损 | SIZE | 不在枚举内 |
| S020 | 可读有损 | ID | ID 含空白 |
| S021 | 可读有损 | ID | ID 与文件名不一致（仅对现行命名方案的文件检查） |
| S030 | **不可用** | MEMORY_BODY | 正文为空 |
| S031 | 可读有损 | MEMORY_BODY | 正文过短（不足 10 字） |
| S040 | 可读有损 | KEYS / CONCEPTS / ENTITIES / RELATED_IDS | 列表字段用了分号（应改逗号） |
| S050 | 可读有损 | TITLE | 标题过长（超 200 字） |
| S051 | 可读有损 | TITLE | 标题含换行 |

### 校验的分级原则

- **`KEYS` 从不当必填。** 全库 509 条里 242 条没有 `KEYS`。缺了先看 `CONCEPTS`（S005 可读有损）；两个都没有才判 S004。把这个字段当必填会误判近一半记录。
- **`READ_WHEN` / `NOT_FOR` 缺失只是 WARN。** 记录照样能读、能搜到，只是召回精度低一些。
- **不可用只有五条：R001、R002、S002、S004、S030。** R001/R002 是整体无法解析，S002 是缺 ID 或 TITLE 到无法识别，S004 是连检索入口都建不起来，S030 是正文为空。除此之外一律可读——记录有瑕疵不等于记录作废。
- **`SUPERSEDED` 的记录仍然可见。** 只有 `DELETED` 才排除。

## 六、写入时的保证

校验不只是「检查一下」，写入路径上是硬门：

1. **写入前跑同一套校验。** 不合格直接拒绝并给出规则编号，不会写进去。
2. **只改目标字段所在的字节区间。** 改 `SESSION` 就只动 `SESSION` 那个值，同行的其他字段、字段布局、标点、换行一个字节都不碰。
3. **值没变就不写。** 内容相同直接跳过，不会因为「跑了一次」就刷新时间戳。
4. **写完立刻复读比对。** 解析后重新渲染必须与原文逐字节相同。
5. **写类命令默认只预演。** `repair`、`refresh`、`normalize`、`recount` 不加 `--apply` 只报告将要做什么，不落盘。
6. **失败保留最近有效版本。** 临时文件 + 复读 + 原子改名，任一步失败都不会留下半个文件。

第 2 条是这套工具的核心不变量。历史上的真实事故是：改一个字段，工具重排了整个头部布局，把打包成单行的 `ID=…;PROJECT=…;TASK=…;SESSION=…` 炸成四行，还顺手把全角标点统一成了半角，一次波及 92 条记录。现在的实现按字节区间拼接，这个问题在结构上不可能再发生。

---

## 七、怎么用这些编号

拿到一个报错时：

```bash
abook check <文件>        # 看这个文件触发了哪些规则，附原文与建议
abook audit               # 全库扫一遍，按规则归类
abook doctor              # 只报不可用的（R001/R002/S030）
abook repair              # 预演可自动修的（K 系列、S 系列的部分）
abook repair --apply      # 确认后真正修
```

编号是稳定的，可以写进脚本判断，也可以用来查这份文档。
